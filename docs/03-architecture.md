# 技术选型纪要（方案对比结论）

## 对比结论

| 方案 | 概要 | 结论 |
|------|------|------|
| **A** | 原生微信小程序 + **微信云开发**，轻量定制 | **工作基线（采用）** |
| B | 芋道等整栈开源（Spring + 管理端 + 商城模块） | 不采用为 MVP 基线 |
| C | 其他开源商城 / 低代码 | 未选定为基线 |

### 选用 A 的主要依据

- **校服域定制重**：区县隔离（district）、每区一款、虚拟自提点、合规文案与自愿声明，需贴合小程序体验
- **营销通用模块轻**：MVP 不需要完整 CRM/促销引擎
- **预算与主体未知**：不宜前期绑定 ECS、RDS、独立域名与运维面
- **芋道（MIT）但商城 SQL/部分模块存在星球商用条款风险**，与当前「主体未定、快速验证」不匹配

## 运行时架构（MVP）

```text
微信小程序（原生）
    ↓ 云开发 SDK
云函数 + 云数据库 +（可选）云存储
    ↓ 占位 / 可插拔
微信支付（未接）  物流 API（未接）
```

## 云数据库集合（初稿）

| 集合 | 用途 |
|------|------|
| `districts` | 区县 code、名称、是否开放、排序 |
| `products` | 区属商品，类型套/单，关联 district |
| `skus` | 尺码、价格、库存、关联 product |
| `pickup_points` | 每区 1 个虚拟自提点 |
| `orders` | 订单头：用户、区、履约、支付状态、售后状态 |
| `users` | 微信 openid 等最小用户信息（不含学生身份） |

## 云函数（初稿）

| 函数 | 职责 |
|------|------|
| `listCatalog` | 按 district 返回商品 + SKU + 自提点摘要 |
| `createOrder` | 校验库存、写订单、扣减/锁定策略按实现阶段定 |
| `mockPay` | **仅测试**；将 `payStatus` 置为 paid，日志与 UI 标注非真收款 |
| `adminAdjustStock` | 运营加减库存 |
| `pay` | **空实现 / 占位**，商户号就绪后接入 |
| `shipping` | **空实现 / 占位**，对接物流时接入 |

## 数据关系草图

```text
District 1 ── * Product (套 | 单)
                 └── * Sku (size 110–180, stock)

Order
  ├── districtId
  ├── items[]: { skuId, qty, priceSnapshot }
  ├── fulfillment: express | pickup
  ├── pickupPointId? (pickup 时)
  ├── address? (express 时)
  └── payStatus: pending | paid
```

## 风险与缓解

| 风险 | 说明 | 缓解 |
|------|------|------|
| 主体 + 商户号 | 真支付与提审的**上线闸** | 文档与代码预留 `pay`，MVP 用 mock + 文案 |
| mock ≠ 真支付 | 误用 mock 造成合规/资金风险 | 环境隔离、界面与日志强制免责声明 |
| 区县 × SKU 矩阵 | 多区多尺码维护成本 | 后台加减 + 种子数据脚本（后续） |
| 合规文案 | 强制选购表述、采集学生信息 | 产品审阅固定模板，Gate 1 验收 |

## 非目标（架构层）

- 不创建付费云资源（按环境实际开通为准，文档不预设 ECS/CDN 账单项）
- MVP 不接真支付、不对接真实学校与物流
